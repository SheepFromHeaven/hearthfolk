# Hearthfolk

Player-facing name Hearthfolk (renamed from MineNow). The mod id, packages, config file (`minenow-local.toml`) and data namespace stay `minenow`, so renaming never breaks worlds.

NeoForge 26.3 mod (NeoForge `26.3.0.101`, mod loader plugin `net.neoforged.moddev`). Group/mod id: `com.sheepfromheaven.minenow`. Java 25.

## Vision

Vanilla villagers that get better at their existing professions in the farms and workshops the player builds. No custom
mob, no town banner, no screens. Vanilla already provides houses (beds), workplaces (workstations), growth (breeding)
and schedules; we only add behaviours to the villager brain. Professions are added one at a time, farmer first.

## Source layout (`src/main/java/com/sheepfromheaven/minenow/`)

- `MineNow.java` — mod entry point, event wiring, gametest registration
- `MineNowConfig` — switches (a `LOCAL` config: this FancyModLoader has `LOCAL`/`SYNCED`/`CLIENT`/`STARTUP`, no `SERVER`), file `config/minenow-local.toml`. A `LOCAL` file is one per game, not per world: NeoForge loads it from the game's config folder at startup (`CommonModLoader`, `FMLPaths.CONFIGDIR`), every world shares it, and FML's file watcher reloads it when it is edited while the game runs (unless `disableConfigWatcher` is set in `fml.toml`), so edits apply live. Top level: `villagersSummonGolems` (default false, see `golemsmith/`), `travellingMerchants` (default true, see `villager/Exports`), `inkAndQuillRecipes` (default false, see `cartographer/`) and `maxMerchantTours` (default 4, see `merchant/`). The `[features]` section has one switch per system, all on by default (`MineNowConfig.Feature`, each with a comment saying in player terms what turning it off does): `villagersDefendTheVillage`, `villagersEatMeals`, `villagersPayEachOther`, `villagersFollowEmeralds`, `villagerChestsLocked`, `villagersPreferRoads`, `villagersLevelThroughWork`, `villagersGetNames`. `MineNowConfig.enabled(feature)` reads it live (on before the config has loaded), so a behaviour checks it in `checkExtraStartConditions` and `canStillUse` and an event listener at its top; no brain rebuild needed. Tests of a feature switched off run in its `feature_<name>` test environment (`feature_villagers_eat_meals`, ...: work hours plus `minenow:feature_off`, our own environment type, `gametest/FeatureOff`, which turns the switch off when its batch starts and back when it ends), so the whole batch sees it off and no other batch does; `every_feature_is_on_by_default` checks the defaults. Tests that flip one of the top-level switches restore it in a `finally` and run in the `config` test environment, so the flip never reaches tests in other batches
- `villager/BrainHook` — adds our behaviours to every adult villager's brain (re-applied whenever vanilla rebuilds it), after `VillagerBrains` rebuilds it from vanilla's packages: MEET and IDLE without `TradeWithVillager` (no handing food/goods to each other; goods move by trading), farmers with `FarmerWork`'s WORK package, CORE with `PanicOrFight` in place of vanilla's panic trigger (plus a FIGHT activity for it), and `WalkToPoi` in place of vanilla's walks back to the job site, bed and meeting point
- `villager/WalkToPoi` — keeps a villager's job site, bed and meeting point on a walk across the village. Vanilla's `SetWalkTargetFromBlockMemory` gives the place up once `CANT_REACH_WALK_TARGET_SINCE` is over a minute old, but every walk sets that (a walk to anything past a villager's 16-block follow range only ever gets a partial path), and beyond 100 blocks (150 for the bed) it gives the place up outright. The job site is never given up for being out of reach (`WalkToPoi.keeping`), only once its block is gone, which is checked wherever the villager is (vanilla's `ValidateNearbyPoi` only within 16 blocks); two villagers of one trade holding the same block is still settled by vanilla's `PoiCompetitorScan`. For the bed and meeting point only failing to reach the place itself, from within 16 blocks of it, counts: a streak of failed walks to it lasts while that timestamp stays the same, so whatever clears it (a miner down its mine) ends the streak as in vanilla. Villagers have vanilla's default follow range of 16, so no path is ever planned further than that: anything further is reached by partial paths
- `villager/ChooseMeetingPoint` — each late afternoon a villager drops its bell and claims the nearest one it can reach from where it is (48 blocks, within the bell's 6-block reach), so meeting points vary day to day; the bell it claims makes it one of that bell's village (`Villages`)
- `villager/Villages` — a village grows out of its bells: every villager's claimed bell, bed, job site and chests are its places (the anchors), a villager's places belong together, and places within 32 blocks of each other across (48 up or down) join up, whoever's they are, so beds and workshops between two bells make them one village however far apart the bells are. Each group of places with a bell in it is a village, its area everything within 16 blocks of its places; a villager belongs to the village its places are in (none if they hold no bell), or one with no places to the village it stands in. A banner on a hay bale is a place too that nobody has to claim (`Villages.addMarkers`: found through the archer post POI, which indexes every hay bale, one query per occupied cell of the grid, and only when a place is within 32 blocks of it, so decorative banners cost nothing and link nothing): it links the places within 32 blocks of it, so a bed too far from the bell joins the village through a marker in between; markers don't chain through each other, and one near no place is ignored. Joining uses a 32-block grid, so it stays cheap with hundreds of villagers. Rebuilt every 100 ticks from the villagers loaded in the level (sooner for a villager that claimed a bell it's not listed under yet), never saved. Trading and commissions stay inside a village; the alarm covers all of it (`Alarms`). Gametests are laid out 5 blocks apart, so two tests with bells in one batch are one village: each test with a bell has an environment of its own (`village_1` to `village_43`, work hours), and those needing two villages use `structure/field_72x8x24.nbt`
- `villager/HomeStorage` — each adult villager claims one chest within 8 blocks of its bed (custom `home_storage` POI on chests), or failing a free chest a barrel (`HomeStorage.isStoragePoi`: chests or vanilla's fisherman POI, which every barrel is; taking the barrel's ticket means no villager takes it as a workplace, and a barrel that's someone's job site is never taken, nor released by `releaseChest`, but only while that villager is alive: a fisherman dying released nothing and left his barrel locked for good, so `heldAsJobSite` skips the dead, and a click on a lock of ours that no villager holds lifts it, `liftAbandonedLock`, for barrels locked before that fix), locks it for players, releases it on death/conversion; right-clicking it says whose it is. Breaking it isn't theft (the player may be rebuilding): its contents drop as the villager's (`Belongings`: vanilla's item target keeps players from picking them up, no despawning), the villager gathers them back (`Belongings.Gather`, any adult while awake) and its unloading puts them in its next chest; `/minenow free` frees every claimed item within 32 blocks (`Belongings.freeNear`: no owner, no pickup lock, so the villager leaves them too), for a player's things that a villager's claim had locked; once the villager dies or zombifies they're ordinary items. A hopper or hopper minecart swallowing them is theft by its placer (`Belongings.onEntityLeave`, the owner read from the item's vanilla target since attachments are gone by then; `BREAK_GOSSIP` per stack); its own gathering clears the target first. `ModVillagers` holds the POI type and the `storage`/`placed_by` data attachments. What a player has taken is never claimed: a chest or barrel that already holds items (`HomeStorage.holdsItems`, either half of a double chest, checked when the claim is made, here and for workshop chests; tests that want goods in a villager's chest fill it after the claim, `GameTestHelpers.fillOnceClaimed`), and a bed a player has used (`PlayerBeds`: `CanPlayerSleepEvent`, and at login the respawn bed, take the bed's `HOME` ticket the way a barrel's ticket is taken, so no villager can claim it, and a villager already holding it loses it: its `HOME` memory is erased and the player's claim replaces it)
- `villager/Workshop` — workshop storage: a working villager also claims the chests within 6 blocks of its job block (2 up or down), the nearest first, as many as its level (novice 1, master 5), checked every 2 s with the home chest (`HomeStorage.onEntityTick`). Plain chests (`home_storage` POI) and, after the chests, barrels, so a trapped chest is always the player's; a fisherman's own barrel is always its first workshop storage, locked, without touching its job ticket, so its catch goes straight in (unless the barrel already held items when he took it as his workplace and isn't yet his storage: those are the player's, so it stays open and he keeps his catch at home); a chest is one villager's home chest or one workshop's, never both. Locked, shown as theirs, broken and drained like a home chest. Trade goods are unloaded there and food and emeralds at home (`Workshop.personal`; `Unloading.unloadTarget` picks the chest, `deposit` only puts in what belongs; with only one kind of chest everything goes there, and trade goods go home when the workshop is full); after unloading at one, a villager with goods left for the other finishes the round. Economy counts, takes and gives over home and workshop chests (`Storage.chests` outside the package). The chests go with the job site: released when the job's lost. `villager/Walking.towards`: a behaviour walking further than 9 blocks from its job site (to a home chest) re-pins its walk target, since vanilla's work package keeps pulling villagers back
- `villager/Economy` — a villager's goods are its inventory plus its home chest and workshop chests: counting, taking, giving, and the one-time starting purse (6) granted when it first takes a job (`BrainHook`, so children bring money into the village when they grow up and get a job), once per villager for its whole life: a new job brings nothing, and the `purse_granted` flag survives zombifying and curing (`copyOnDeath`, copied on conversion). When buying from players or other villagers a villager never goes below its `reserve`: 2 emeralds food money plus the price of the cheapest tool of its trade (a villager with no tool may spend down to the food money on one, and likewise one of a fuel-burning trade with no fuel on fuel, and food may use the food money), so a crafter without customers pauses with full shelves instead of going broke (between villagers only while they pay each other); every supply offer shares that one purse, so after each purchase the others are capped to what's left. The other sources of new money are the miner digging emerald ore and exports (`villager/Exports`). `GameTestHelpers.spawnEmployed` leaves the purse out (tests hand out the emeralds they need, `giveStartingPurse` adds it). The `villagersPayEachOther` switch has one seam here: `Economy.pay(level, from, to, emeralds)` is every payment from one villager to another (`to` null: emeralds that leave with a travelling merchant) and does nothing while it's off, and `Economy.villagerBudget(budget)` is what a villager may spend on another villager's goods, no limit while it's off; `Economy.villagersPay()` reads the switch. Off, villagers take what they need from each other for free, outside villager trading too: the cleric's healing potion (`HealVillagers`), a village merchant's cargo, invisibility potion and bedding wheat (`Tours` sizes the shopping list by free slots alone, `Camp`), while the travelling merchant still pays for exports. Player trades always cost emeralds whatever the switch says: a player pays a villager, and a villager pays a player out of the emeralds it holds within its `reserve` (`ProfessionTrades`, `budgetFor`, never routed through the seam). The starting purse and emeralds villagers hold are left alone
- `villager/WorkXp` — levelling through work: `WorkXp.award(villager, xp)` adds vanilla villager experience and runs vanilla's level-up (new trades, via access transformers on `shouldIncreaseLevel`/`increaseMerchantCareer`), so skills scale with work, not only with trading with players. Capped at `DAILY_CAP` (24) per villager per game day (`work_xp_day`/`work_xp_today` attachments), about ten days of steady work from novice to master; none for unemployed or nitwits. Amounts are decimal and carried over (`work_xp_progress`) until they add up to a whole point; the per-action constants live in `WorkXp`: 0.05 per block dug, 0.1 per crop harvested or road block paved, 0.2 per log felled, 0.5 per furnace output collected or flower bone-mealed, 2 per enchanted book bound, 1 per catch, sheep sheared, animal culled, item crafted (`CraftAtWorkstation`), blade restored, piece dyed, armor piece displayed or archery round. A new work behaviour should call it too. `GameTestHelpers.spawnEmployed` villagers have used up their day's experience so a level a test sets stays put (`allowWorkXp` gives it back)
- `villager/TradeTable` — per-profession prices and level unlocks from `data/<ns>/villager_trades/<profession>.json` (reloads with `/reload`); every price is one decimal number of emeralds per item (0.05 is 20 for an emerald, 3 is one for three; `villager/Price` turns it into the smallest whole-emerald deal, the same for players and villagers); `tools` are bought when the villager has none, `produce` is sold at its `price`, `supplies` are bought at their `price` in that deal's batch while the villager holds less than one batch in its goods (chests included, or a batch bigger than `max` went to the chest and it bought again), and it keeps up to `max` on it, taking supplies (and a tool of its trade, when it has none on it) back out of the chest when it unloads (`Unloading.restock`), since its work only uses what it carries; a tool of its trade it's given with full pockets and none on it goes in its pockets, another stack going to the chest (`Economy.give`), `default_produce` prices anything in a set (farmer: `#c:crops`, 0.05) that has no `produce` entry, `keeps` lists goods the villager makes and works on further (kept up to `max` when unloading, never bought), and `crafts` lists items it makes at its workstation from `materials`, `count` at a time (default 1), wearing the tool of its trade `tool_uses` times (default 0), priced by `TradeTable.craftPrice`: materials (valued at its own supply price, else what it sells them for, crafts included) plus decimal `labor` plus tool wear (cheapest tool's price over its durability, per use), split over `count` and sold in the smallest whole-emerald batch like any price; things that don't stack (tools) are one item for whole emeralds, rounded up. A `produce` entry overrides a craft's price. Several entries for one item at different levels: the latest unlocked one is the recipe (`craft(item, level)`), so a level can make something cheaper; several entries at the same level are alternatives (sticks or shields from any planks), all used. A crafter keeps `stock` but never less than one sale's batch (`stockTarget`), so it always has a whole batch to sell. `TradeTable.sellPrice` is the one lookup: produce entry, then craft, then `default_produce`; a level unlocks its entries and keeps earlier ones
- `villager/ProfessionTrades` + `Unloading` + `PickUpGifts` — profession-neutral: any villager whose profession has a trade file gets data-driven offers (buys a tool of its trade when it owns none, sells produce, buys supplies), keeps one tool / supplies up to `max` / seeds and food up to 16 and deposits the rest in its home chest, and walks over to what it needs lying within 10 blocks in its sight, as a player would throw it (`PickUpGifts`, since vanilla only walks to wanted items when nothing else sets its walk target): a tool of its trade when it has none, first, else a supply it's short of, up to the supply's `max`; else emeralds, up to what it needs to start a family plus its reserve (`PickUpGifts.emeraldCap`: `Wealth.required` + `Economy.reserve`, so a player can fund a villager but not flood it); never items that belong to another villager. `BuyFromVillagers` stands aside while it runs. Supplies are bought and picked up only when needed (`TradeTable.suppliesWanted`, `SupplyNeeds`: a profession registers when a supply it covers is needed beyond being short of a batch; the farmer's seeds only with no field seed in its goods and farmland or tillable ground in its field with nothing on it, `FarmerReport.needsSeeds`); unloading still keeps them. A trade file's `tool_tag` (farmer `#minecraft:hoes`, fisherman `#c:tools/fishing_rod`) decides what counts as its tool, so modded tools work
- `villager/JobLoss` — vanilla's `ResetProfession` only takes the trade from a job-less villager with no experience and level 1, and work experience (`WorkXp`) ends that at the first catch or harvest, so a villager whose job block was lost or moved away kept its trade for good and no other job block could change it. A villager with a profession and no `JOB_SITE` memory for a full day (`JobLoss.PATIENCE`, the `no_job_since` attachment, checked with the home storage every 2 s) that is still level 1 becomes unemployed again (experience kept), so it can take another job block; higher levels keep their trade. A job site whose block is gone, or whose point of interest is no longer one its profession holds (`VillagerProfession.heldJobSite`: a chest standing where the barrel was is a point of interest, `home_storage`, but no fisherman's), is forgotten by `JobLoss` itself too (`forgetGoneJobSite`, every 2 s, a place in an unloaded chunk every 30 s through the POI storage): `WalkToPoi` only notices it while the villager works and the place is loaded, so a villager moved away from its barrel, or one resting at night, kept the memory of the broken barrel (the report showed its old position as the job site) and the day-long countdown never started. The villager report has a job line (`JobLoss.describe`): the job site position with the block and point of interest found there, or that there is none and in how many minutes of game time the trade lapses
- `villager/Meals` + `EatMeals` — every adult villager eats twice a day (`last_meal` attachment, 12000 ticks): food from `#minenow:villager_meals` (bread, vegetables, fruit, cooked meat and fish, ...) worth 6 nutrition, most filling first, from its inventory or home chest. A balanced diet: it alternates bread, vegetables and the like with cooked meat or fish (`last_meal_meat` attachment), eating the other kind than last time when it has a meal's worth of it With `villagersEatMeals` off (`Meals.on()`, read live) nobody eats: `EatMeals` never starts, `Meals.isHungry` says no, so `BuyFromVillagers` skips the hungry buyer, the next-meal buyer and `mealGift`, while buying breeding food (`Wealth`) stays and `Economy.reserve` keeps its 2 emeralds of food money; `last_meal` and `last_meal_meat` are left alone, so turning it back on makes villagers hungry at their next meal time. Its tests (`without_meals_*`) run in `feature_villagers_eat_meals`
- `villager/Wealth` + `WealthFormula` — wealth pays for children: a villager with enough emeralds in its goods (`Wealth.required`) and under vanilla's 12 breeding food points buys one emerald's worth (food in its chests counts, or it would buy again every time it unloads); vanilla breeding does the rest (partner, free bed). What counts as enough grows with the village: `data/<ns>/wealth/breeding.json` gives `base + per_villager * members of its village` (members from `Villages`, 1 with no village), rounded up and kept between `minimum` and `maximum` (default 3 + 1 per villager, 4 to 40; reloads with `/reload`). The members include children, so a crowded village stops growing until it is richer
- `villager/BuyFromVillagers` — villager-to-villager trading: a hungry villager without a meal buys the most filling food for its money (an emerald buys far more carrots than bread), a villager with money above its reserve buys some of the other kind of food for its next meal, a hungry villager with no meal and no money is given one by a neighbour holding more of a food than it could sell (`Exports.bulk`; vanilla villagers share food, here only with those who can't pay), and a wealthy one short of breeding food buys one emerald's worth from the nearest seller (any time it's awake); while it works, meets or idles (a miner is down its mine all working day, so its coal and ore could only be bought after work), a villager holding less than one batch (`count`) of a supply of its trade in its goods, with emeralds, walks to the nearest villager of its village that sells it, however far (a villager of no village trades with those within 48 blocks that belong to none either; two villages never trade), giving up after 30 s plus a second per block past 24 (`TradeTable.perEmerald`: a `produce` entry or `default_produce`, unlocked at the seller's level) and buys at the seller's player price, as many emeralds' worth as it can afford, the seller can spare (goods minus what it keeps) and fits under the supply's `max`. Goods and emeralds move through `Economy`, so home chests count. First case: the butcher buys wheat from the farmer. Trades need line of sight (no buying through glass), and a seller down a mine is skipped (buyers fell in after it). Prices are the smallest whole-emerald deal, so cheap goods come in big lots (raw copper 50 for 3 emeralds); a seller short of a whole lot sells an emerald's share instead (`lotFor`). Credit: a craftsman too broke to pay for a tool or a supply of its trade takes one lot on account from a seller with a lot to spare (not while resting), up to `CREDIT_LIMIT` (3) emeralds owed in all (`debts` attachment), and pays it back from earnings above its reserve, so a smelter with no ore or a butcher with no fuel can start. The offers a player sees follow the same budget (`BuyFromVillagers.budgetFor`: fuel it has none of may use everything above its food money, else only above the reserve), or a butcher at its reserve with no coal had no offer at all and just shook its head. A trade that buys fuel (butcher, smelter) buys what it cooks only once it holds fuel (`waitsForFuel`), or it spent its purse on fish it could never smoke. A supply no villager sells may be bought from a travelling merchant within 48 blocks (`BuyFromVillagers.merchantDeal`, after villagers and before credit and commissions; the merchant belongs to no village, so any villager near it may buy): at the merchant's own offer, out of what's left of its stock (each lot uses the offer up, so players and villagers share it), paid from what's above the buyer's reserve (fuel it has none of may use everything above its food money), up to the supply's `max`; only `Exports.isMerchant` traders, never vanilla's wandering trader. Tests with a merchant each have an environment of their own (`merchant_1` to `merchant_8`, work hours): the merchants and the villagers selling string in neighbouring tests are within range. The emeralds leave the village with the merchant, the counterpart of what it pays for exports. Tool upgrades: a working villager with money above its reserve buys the best better tool of its trade a crafter has (further down its trade file's `tools`, which run worst to best, unlocked at its level), throwing its old one away (nobody buys a worn tool); a miner whose pickaxe can't harvest something in its mine (`Miner.pickaxeHoldsItBack`: ore down to its depth) takes the cheapest better one on credit, since a wooden pickaxe leaves iron and copper ore in the walls. With `villagersPayEachOther` off every payment and budget here goes through `Economy.pay` and `Economy.villagerBudget`, so nothing is paid and money limits nothing: a deal is what the buyer needs (up to a supply's `max`, one tool, one meal's lot, the best gear piece, the best tool upgrade) and what the seller can spare (keep limits and `Commissions.reserved` still apply), the travelling merchant's supplies are taken free but still use up its offer, breeding food is fetched whenever it is short of 12 points (`Wealth`), no credit is given (`creditDeal`) and old `debts` are frozen (`repayDebts` reduces a debt by what `pay` moved, so they're repaid as before once it's back on). The answers it gives other code follow the switch too: `demand` and `needs` count what villagers need rather than what they could pay for (merchant visits and tours), and `canBuySupplyFromAVillager` (`Shortage`, `IdleReason`) and `couldBuyTool` (`Miner.breaksThrough`) only ask for a seller with one to spare; `NO_MONEY` and `SeekGoods`' emerald still count money, since they are about paying a player. Its tests (`without_payment_*`) run in `feature_villagers_pay_each_other`, the broke merchant's tour in `feature_villagers_pay_each_other_tour` (the 72-block field), the commission one in `feature_villagers_pay_each_other_commission` (the same switch off, a batch of its own: a broke farmer in a neighbouring test took the armorer's only order slot)
- `villager/Commissions` — work paid for up front, so money pooled at the trades everyone buys from reaches the ones that make things: when nothing is to be bought (`BuyFromVillagers.newCommission`), a villager with money to spare (`Gear.budget`) orders a piece of gear nobody has in stock from a villager of its village that makes it (unlocked at its level), a working villager a lot of a supply of its trade nobody can spare from one that sells it, or a wealthy one has a powered mason pave the dirt path to its home; it pays the maker's price at once, so the maker can buy what it needs (farmer pays the armorer, the armorer the smelter for copper, the smelter the miner for ore). One open order per buyer. The order lives on the maker (`ModVillagers.COMMISSIONS`: buyer, item and count or path start, paid, placed) and the buyer remembers whom it paid (`COMMISSIONED`), both data attachments, so a restart loses nothing (`commission_survives_a_restart` saves and reloads both villagers). The maker crafts what's ordered on top of its stock and holds it back from other buyers, merchants and bulk (`Commissions.reserved`); the buyer collects it once the maker has it (gear goes straight on). Undelivered after `EXPIRES` (3 days) the buyer asks for its money back (a paving order only once the mason has stopped paving); an order whose buyer never came is dropped after twice that, and a buyer whose maker is gone forgets it then. With `villagersPayEachOther` off orders are still placed (they make makers produce what nobody has in stock) but free, `paid` 0; an order paid before the switch went off still refunds its real emeralds, a free one refunds nothing
- `villager/Exports` — the village's exports: goods only players would otherwise buy (`#minenow:exports`: armor, swords, shields, bows, crossbows, saddles, leather horse armor, bundles, and the golemsmith's iron bars, buckets and cauldrons). Once a minute near each player (`Exports.visitNear`, unless the `travellingMerchants` switch is off), if no wandering trader is within 96 blocks, the export goods of the villagers within 48 blocks draw a travelling merchant with `Exports.visitChance` (together with the village's needs, `BuyFromVillagers.demand`: for each supply of its trade a villager is short of that the merchant carries and no villager in its village sells, the emeralds it could spend on whole lots above its reserve and under the supply's `max`) (none under 8 emeralds' worth, rising to 50% at 64), at most one every 5 minutes, onto open ground near the villager with the most. The merchant is a wandering trader marked `TRAVELLING_MERCHANT`, named "Travelling Merchant", with two chested pack mules on leads instead of llamas (`PACK_MULE`; they leave with it, and an untamed one without a lead disappears), selling goods from afar the village can't make (`data/<ns>/travelling_merchant/*.json`, all files merged, one decimal price per item like the trade files, items of missing mods skipped; by default string, sugar cane, cocoa beans, sweet berries, honeycomb, nether wart, and what a cleric brews with: blaze powder, gunpowder, spider eyes, brown mushrooms) instead of vanilla's random trades. It walks to villagers within 24 blocks holding export goods and buys them at the villager's own price, in whole batches, with new emeralds, up to 32 per merchant; with what's left it buys bulk surplus at half price (`Exports.bulk`: anything a villager sells beyond what it keeps and beyond half a stack, so a miner buried in cobblestone or a fisherman in fish still earns, and the merchant can't empty the village of anything), which also counts towards the visit chance. In a village (`Villages.at` its position) it first walks to the nearest bell and announces its market there (`Exports.holdsMarket`: the bell's sound and notes, never a real ring, which would send every villager into hiding or to its post), then waits at the bell for 2 minutes (`Exports.openMarket`) before it goes round the villagers to buy; it gives up on a bell it hasn't reached in a minute, and without a village it goes round at once. While the market is open every villager of that village short of a supply of its trade comes to it, however far (`Exports.marketsOf`, used by `BuyFromVillagers.merchantDeal`), and one that polled before the announcement polls again at once (`Exports.lastAnnounced`). Vanilla's own wandering trader stays vanilla and buys nothing
- `villager/Gear` + `PanicOrFight` — villagers buy, wear and use armor and swords. Armor goes in its armor slots, worn all the time (vanilla protection applies, a guaranteed drop on death, kept by a zombified villager), and wears down with the blows it takes like a player's (`Gear.onDamage`; vanilla never wears mob armor). A weapon is kept at its side (`SIDEARM` attachment, not goods, so it's never sold or exported) and drawn only to fight: a sword, or for archers a bow with arrows in a quiver (`QUIVER` attachment). About one villager in three is an archer for life (`ARCHER` attachment, defaulting from its UUID via `Gear.prefersBow`); weapon and arrows drop on death and conversion. - `villager/OpenFenceGates` — shepherds and butchers plan paths through closed fence gates (`RoadNavigation` treats them as walkable doors for them), open the gate on their path once right at it (1.2 blocks) and close it as soon as they're clear of the gateway and not about to pass back through; an animal caught in the gateway when it closes is shooed back one block, away from the villager, so animals stay in; other villagers still only open doors
- `villager/ToolCare` — better craftsmen wear their tool less: chance a use wears it, 100% novice down to 40% master (fisherman and shepherd; the farmer's hoe and butcher's axe are unaffected, those trades improve through better tools instead)
- `villager/Tools` — the tool of a villager's trade: shown in hand as a copy while working, worn down by use
- `client/` — `SwingingVillagerRenderer` replaces vanilla's villager renderer (registered in `MineNowClient`, with its own model layers `minenow:villager` and `minenow:villager_no_hat`: vanilla's villager mesh plus a pair of free arms built from the crossed arms' sleeve and forearm texture, so profession clothing fits). A villager holding a tool or weapon (`HeldItemLayer.gripped`: tool or weapon component, or `#c:tools`) uncrosses its arms and holds it in its right hand like a player, chopping with it on a swing and swinging both arms while walking; anything else lies on its crossed arms as in vanilla, and the crossed arms rise and fall with a swing. `VillagerArmorLayer` draws worn armor with vanilla's zombie villager armor models fitted to the villager (a pixel lower, deepened over the robe, sleeves only on free arms); a helmet replaces the profession hat. With Entity Model Features installed (and the packs built on it, like Fresh Animations) none of that replaces vanilla: EMF reworks vanilla's villager model, found by vanilla's layer names, so vanilla's villager renderer stays and only `VillagerArmorLayer` is added to it (`MineNowClient.keepsVanillaVillagers`, `EntityRenderersEvent.AddLayers`, the armor's state attached to vanilla's render state through `RegisterRenderStateModifiersEvent` as `VillagerArmorLayer.ARMOR`): villagers keep crossed arms and EMF's animations, tools lie on their arms as in vanilla, and helmets don't hide the profession hat
- `dev/GametestPlayground` + `PlaygroundLabels` + `client/GametestPlaygroundWorld` — the `runGametestPlayground` run: opens a fresh creative test world and starts the player in a hub with one portal per `gametest/TestGroup` (framed in the group's concrete, labelled with its test and failure counts); each group's district (coloured wool floor and a big sign: Villagers yellow, Home storage red, Roads light blue, Farmer lime, Farmer trading purple, Fisherman cyan, Shepherd white, Butcher brown, Villager trading orange, Toolsmith gray, Miner black, Forester green, Fletcher pink, Armorer light gray, Smelter blue, Mason magenta, Leatherworker terracotta, Merchant hay bale walls on coarse dirt, Librarian bookshelf, Weaponsmith polished andesite, Golemsmith smooth stone, Village defence cracked stone bricks, Village mossy cobblestone, Cartographer sandstone; layout in `PlaygroundLayout`) sits 1024 blocks from the next, force-loaded so tests tick and labels update, with a portal back to the hub. Tests are idle, each with a floating label (readable name, plus the failure message once it fails; the test block's beacon shows the status) and an overview board with totals and failing tests. `/minenow playground runall` starts them all. Behind the arrival point `PlaygroundShowcase` lines up frozen villagers (no AI, invulnerable, named after what they show) to inspect rendering: holding and swinging the tool of their trade, each kind of armor, fighting with sword or bow, and showing goods on crossed arms
- `soak/VillageSoak` — a long-run economy check, not a test: `./gradlew runVillageSoak [-PsoakDays=50]` builds twenty villagers (workshop, bed, chest, purse and a starting tool each) on a stone slab with ores in it, plus four spare beds with chests and a free smithing table and fletching table, so wealth can turn into children who grow up and take a job, a dirt-path street past each row's beds and a redstone block under the mason's stonecutter (so it paves and takes paving jobs), a bell in the middle (so they make one village; the population line counts villages and villagers in one), lays 40 layers of ground (below the structure too, so an expert's mine doesn't run out, and 24 blocks past its sides underground, so the edge mine's tunnels stay in the ore), sprints the server and writes `soak-report/days.csv` (emeralds, food, goods, export goods, hungry, idle per profession per day, plus livestock) and `soak-report/final.txt` (every villager's pockets and chests). A visiting player (a mock player in creative) stands in the middle, so travelling merchants can come; `-PsoakPlayerBudget=N` has it spend N emeralds a day on random goods through the trade event (`-PsoakPlayer=false` leaves it out; `-PsoakBell=false` leaves the bell out, so there's no village and no afternoon meeting, as in runs before villages). `-PsoakTrace=name#1,...` writes `trace.txt` (activity, behaviours, walk target, goods every minute, every second from `-PsoakTraceFrom`), `-PsoakTraceMines=true` writes `mines.txt` (everyone down a mine), the log reports villagers losing their job sites, and `final.txt` gives each miner's ladder column and next work (with or without a spot to stand) and ends with cross-sections of the mines (stone, cobblestone and other blocks told apart). It only runs with `minenow.soak.only` set (the `villageSoak` run sets it and turns every other test into an instant pass); in the normal gametest run it passes at once. Polls with `succeedWhen`: `onEachTick` schedules one task per tick up to `max_ticks`, which made it crawl
- `src/main/resources/data/minenow/test_environment/late_afternoon.json` — a `clock_time` test environment; tests that need a time of day other than work hours use their own environment so they run in a separate batch instead of moving the clock under parallel tests. The environment's clock doesn't take when its batch is the first after server start, so those tests also call `helper.setTime(GameTestHelpers.LATE_AFTERNOON)`; every test that depends on the time of day must set it, since it otherwise inherits whatever the previous batch left
- `gametest/` — shared gametest helpers (`fence` lays the stone floor and barrier walls; spawning employed/housed villagers). The test structure's own floor doesn't load, so every test must call `fence` first
- Every gametest is registered in `MineNow` with a `TestGroup`; give new tests the group of the feature they test, or add a group (title, wool floor, concrete portal frame) for a new feature
- `src/main/resources/data/minenow/test_instance/` — one JSON per gametest; `structure/field_24x6x24.nbt` is the empty stone-floored test space, `structure/field_72x8x24.nbt` an empty long one for two villages (no barrier roof)

## Dev-only mods

`build.gradle`'s `clientDevMods` configuration (Right Click Harvest + JamLib) is added only to the client run's classpath, for trying compatibility by hand. Never use `runtimeOnly` for such mods: that loads them in `runGameTestServer` too, which changes behaviour under test and makes CI depend on Modrinth.

## Workflow

- **TDD**: write a failing test first, then implement — a GameTest if the behavior needs a live `Level`
  (blocks, entities, ticking), a plain JUnit test under `src/test/java` only if it's pure logic that touches no
  items: on 26.3 item components are bound when datapacks load, so `new ItemStack(...)` throws "Components not bound
  yet" in unit tests. Anything with items is a gametest (they can be instant, see `better_hoes_reap_faster`). See
  `feedback_tdd_workflow` memory.
- **Verify with GameTests, not just compile**: `./gradlew runGameTestServer` (`-Ptests=minenow:name` runs one, `*` wildcards allowed) — a green compile can still hide a broken tag/behavior. Don't declare a task done on compile alone. For pure-logic changes covered by `src/test/java`, `./gradlew test` is the equivalent gate.
- `@GameTest` annotations don't register on this build; tests are wired via `RegisterEvent` + JSON (see `reference_forge_gametest_setup` memory).
- Custom block tags live in `tags/block/` (singular), not `tags/blocks/` — wrong folder fails silently.
- ARGB colors: always include the alpha byte — omitting it renders fully transparent.
- Villager AI: add `Behavior<Villager>`s to vanilla brain activities via `BrainHook`; no mixins unless a vanilla hook is truly missing. To drop a vanilla behaviour, rebuild that profession's brain from `VillagerGoalPackages` the way `FarmerWork` does (only on a fresh brain).
- Access transformers live in `META-INF/accesstransformer.cfg` (declared in `neoforge.mods.toml`); prefer one over a mixin when only visibility is in the way.
- `PathNavigation.createPath` returns null until the mob is on the ground (and never with NoAI); compute paths a few ticks after spawning in tests.
- Villagers never summon iron golems unless `villagersSummonGolems` is on (`Golemsmith.onFinalizeSpawn` cancels `MOB_SUMMONED` golems); vanilla's trigger on 26.3 only needed villagers that slept recently. `LAST_WORKED_AT_POI` is written by vanilla but never read and not even registered.
- Per-villager state that must survive reloads goes in a NeoForge data attachment, not a custom brain `MemoryModuleType`: the brain drops saved memories that aren't registered at rebuild time, and ours are only added afterwards.

## Token-cost hygiene (read before running builds/tests)

- Compile before running gametests: `./gradlew compileJava` first, `runGameTestServer` only once that's clean. A compile error inside a full gametest run produces far more noisy output than catching it standalone.
- Always add `--console=plain -q` to gradle invocations to suppress Minecraft/Forge startup spam (asset indexing, mod discovery), e.g. `./gradlew runGameTestServer --console=plain -q 2>&1 | tail -80`.
- Never dump raw `./gradlew runGameTestServer` / build output into context. Pipe through `grep`/`tail` for the failure only, e.g. `./gradlew runGameTestServer --console=plain -q 2>&1 | tail -80` or `| grep -A20 FAILED`.
- Don't `cat`/`Read` full log files under `run/logs/`, `run/crash-reports/`, or `build/`; grep for the specific error first. (These are also permission-denied for `Read` in `.claude/settings.json` — use `grep`/`tail` via Bash instead.)
- For "find X" or "where is Y defined" questions, use the `Explore` agent instead of reading many files directly in the main conversation.
- Prefer `Edit` over re-reading a file you just wrote to confirm it — the tool already errors on failure.
